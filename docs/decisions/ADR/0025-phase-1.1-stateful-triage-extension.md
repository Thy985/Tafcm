# ADR-0025 Phase 1.1：状态驱动的 Triage 扩展（Stateful Triage Extension）

> **状态**：Accepted（2026-08-30 随 ADR-0025 v1.0 一并追认——Stateful Triage 扩展已实施）
> **版本**：v1.1（addendum to ADR-0025 v1.0）
> **作者**：AI 协作开发者（基于 Human Owner 设计评审）
> **关联**：`docs/decisions/ADR/0025-issue-triage-agent-architecture.md`（ADR-0025 本体）· `.github/workflows/claude-review.yml` · `.github/workflows/issue-triage.yml` · `.github/schemas/findings.schema.json` · `.github/scripts/issue-triage/create_issues.sh`

---

## 背景（Context）

ADR-0025 已**端到端实证跑通**：run `31590878740` 在 `dry_run=false` 下由确定性执行器真实创建了 Issue #147。它确证了「确定性提取 → 不可信只读推理器 → 确定性执行器」三段式链路可用，且 analyze 步零写权。

但当前 review 与 triage 之间的**唯一耦合是 GitHub Comment**：`fetch_input.sh` 用 GraphQL 拉取 PR 未解决评论喂给 reasoner。这正是「把 Comment 当数据库」的反模式，且我们已**亲手用实证踩爆**：

- **Bug 7**：`Field 'createdBy' doesn't exist on type 'PullRequest'` —— Comment schema 脆弱、强依赖外部 API 形态，一变就崩。
- **reasoner（MiniMax-M3）实测**：面对明确 bug 评论仍产出 0 findings，且误写 `trust_level: fork` —— LLM 在 comment 流上的输出不可靠，用作状态源会直接污染下游决策与 fingerprint。

此外，ADR-0025 的 `memory` 当前只是**去重历史**（`issue-triage-history` artifact，90d 过期），没有 open/resolved/stale/escalated 的**状态语义**；reducer 职责**隐式藏**在 `create_issues.sh` 内，没有显式、确定性、幂等的独立组件。

**本扩展的目标**：在不推翻 ADR-0025 已跑通链路的前提下，把它从「评论驱动（comment-driven）」升级为「状态驱动（state-driven）」——扩大覆盖面（不止 Claude Review，可接任意 Engineering Signal），并把原隐含契约显式化。

> 三个职责变化的正式定义：
> - **Comments**：从「数据源」降级为「展示层」（人类界面）。
> - **Memory**：从「去重历史」升级为「系统状态」（含生命周期语义）。
> - **Triage**：从「评论分析器」升级为「状态消费者」。

## 决策（Decision）

### D10. 四层职责模型（Layers）

```
                    Engineering Signals
                             │
       ┌─────────────────────┼─────────────────────┐
       │                     │                     │
 Claude Review           CI / Test           Security Scan
  (producer)           (producer)            (producer)
       │                     │                     │
       └─────────────────────┼─────────────────────┘
                             ▼
                    Review / Signal Result        ← 机器事实层（Machine Fact）
                             │
                             ▼
                   Deterministic Reducer         ← 显式、确定性、幂等
                             │
                             ▼
                    Persistent Memory            ← 系统状态层（System State）
                             │
                             ▼
                       Issue Triage             ← 状态消费者（非评论分析器）
                             │
                             ▼
                    Deterministic Action        ← 执行结果层
                             │
                             ▼
                  Issue / PR Comment / Alert
```

| 层 | 职责 | 性质 | 是否权威状态源 |
|---|---|---|---|
| **Comments** | 人类界面：inline / review summary / general comment | 展示层（可编辑、折叠、解决、过期） | ❌ 否 |
| **Review Result** | 某次 Review/Signal 的结构化产物 | 机器事实（本次结果，非长期状态） | ❌ 否 |
| **Memory** | 经过所有成功 Review 后的工程问题长期状态 | 系统状态（materialized view + event log） | ✅ 是 |
| **Issue / Action** | 按 Memory 派生的执行结果 | 确定性副作用 | 派生，非源 |

**关键规则**：Comment 必须保留，且作为**第一等产物**（人类协作入口），但**绝不反喂 Triage 主链**——Triage 只消费 Memory。失败的 Review 可以产生 Comment，但**不能产生业务事实**（见 D14）。

### D11. Review Result Contract（抽象协议）+ 物理复用 `findings.json`（Phase 1）

抽象协议 `Review Result Contract` 与当前实现文件名 `findings.json` **概念分离、Phase 1 物理复用同一文件**：

- **Phase 1**：不改文件名。`findings.json` 同时承担「reviewer/triage 输出」的载体；我们在 `findings.schema.json` 上**补充契约字段**，把「本次事实」显式化：

```json
{
  "schema_version": "1.1",
  "producer": { "name": "claude-review", "version": "v1" },
  "run_id": "review-001",
  "commit_sha": "abc123...",
  "status": "success",
  "completeness": "full",
  "source": { "type": "...", "pr": 145, "branch": "...", "base": "...", "trust_level": "maintainer", "fetched_at": "..." },
  "summary": "...",
  "findings": [ { "id": "...", "category": "bug", "severity": "high", "confidence": 0.91, "component": "auth", "root_cause": "idle-timeout", "...": "..." } ]
}
```

- 新增字段（建议加入 `findings.schema.json` 的 `required`/`properties`）：
  - `producer: { name: string, version: string }` —— 多 producer 就绪（claude-review / codex-review / ci / security-scanner…），reducer 统一处理。
  - `run_id: string` —— 跨层可追溯锚点。
  - `commit_sha: string` —— 绑定到具体提交。
  - `status: enum[success, partial, failed]` —— 驱动状态机（D14）。
  - `completeness: enum[full, partial, none]`。
- **Comment 回溯**：`claude-review.yml` 在发出的 Comment 中附带 `run_id` + `commit_sha`，使 GitHub 上任意一条 comment 可反查 `review-result → memory history`（可追溯性）。
- **何时改名**：仅当出现**第二个 producer** 时，才将 reviewer 输出物理拆分为 `review-result.json`，triage reasoner 输出为 `triage-findings.json`。Phase 1 不拆文件，先显式化概念。

### D12. Deterministic Reducer（核心新增组件，从 `create_issues.sh` 抽出）

当前 `create_issues.sh` 隐式承担了 reducer 职责（去重/状态判断埋在内部副作用里）。本扩展将其**显式拆出**为独立、确定性、幂等组件：

```
review-result.json
      │
      ▼
reduce_review_state.sh      ← 纯函数：读 review-result + 当前 Memory → 写新 Memory
      │                       （无 GitHub 副作用，不调 gh API）
      ▼
memory/ (state.json + runs/)
      │
      ▼
create_issues.sh            ← 消费 Memory（非评论）→ GitHub Issue / PR comment
```

- `reduce_review_state.sh`：确定性、幂等、可单测（fixture 驱动）。**唯一写入 Memory 的组件**。
- `create_issues.sh`：降级为「Memory → 动作」的纯执行器，不再自行推断跨 run 状态。

### D13. Memory 持久化（**修订 ADR-0025 D6 Phase C 目标**）

ADR-0025 D6 原 Phase C 目标是「仓库内 `.issue-triage/history.json` 落库（commit-bot 写入）」。**本扩展否决该方案**，理由：

1. **并发/merge 冲突新故障类**：多个 PR 同时 review，两个 reducer 各自读旧 state 写回 → 覆盖（feature repo 的 git 提交无法做原子 CAS）。
2. **评审噪音**：state 频繁 churn 进 feature repo，与「comment 进仓库是噪音」自相矛盾。
3. **越权**：Memory 是系统运行时状态，不应与源码同仓演进。

**新目标：专用持久化，不进 feature repo**。选项按成熟度：
- （a）**专用 workflow artifact**（跨 run handoff，retention > 90d）—— 短期可行；
- （b）**单个 state issue**（bot 经办、原地编辑）—— 中等；
- （c）**独立 state 仓库**（reducer 有写权）—— 长期推荐。

**Reducer 运行位置**：在受信 `create` job 内（该 job 本就有写 scope），不违反 ADR-0025 D7「analyze 零写权」边界。

**Memory 布局（Phase 1）**——标准 Event Sourcing / materialized view，无需数据库：

```
memory/
├── state.json            # 可变投影（mutable projection）
│   { "last_successful_review": "...",
│     "current_commit": "...",
│     "findings": { "<fingerprint>": "OPEN|STALE|ESCALATED|RESOLVED" } }
├── runs/<run_id>.json    # 不可变事件历史（immutable event log）
└── findings/<fp>.json    # 每条 finding 的详情（可选）
```

`state.json = 可变投影`，`runs/ = 不可变事件历史`。两者分离即具备审计性与可追溯性。

### D14. 状态机（正式冻结）

最小状态集：`UNKNOWN → OPEN → RESOLVED`，扩展 `STALE`、`ESCALATED`。

```
        new fingerprint
UNKNOWN ─────────────► OPEN
                         │
          successful review confirms absent
                         ▼
                      RESOLVED
                         ▲
          successful review confirms absent │
OPEN ── failed / partial review ──► STALE ─┘
                         │
            stale_age / failure_count > 阈值
                         ▼
                    ESCALATED  （需人工介入，非自动解决）
                         │
          successful review confirms absent
                         ▼
                      RESOLVED
```

转移规则（由 reducer 依据 `review-result.status` + finding 是否仍存在确定性推导）：

| 当前状态 | 输入 | 下一状态 | 说明 |
|---|---|---|---|
| UNKNOWN | 首次成功 Review 确认存在 | OPEN | 进入追踪 |
| OPEN | 成功 Review 确认消失 | RESOLVED | 已被修复 |
| OPEN | 失败 / 部分 Review | **STALE** | **仅改 freshness，业务状态不变** |
| STALE | 成功 Review 确认存在 | OPEN | 复发 |
| STALE | 成功 Review 确认消失 | RESOLVED | 已修复 |
| STALE | 陈旧度/失败计数超阈值 | **ESCALATED** | 需人工介入 |
| ESCALATED | 成功 Review 确认消失 | RESOLVED | 已修复 |

**铁律 ①**：`失败的 Review 只改变 freshness，绝不直接改变 finding 的业务状态。` ⇒ `OPEN + failed = STALE`，**不是** `RESOLVED`。

**铁律 ②（对「自动 RESOLVED」的 pushback）**：STALE **不自动 RESOLVED**。没有证据证明 bug 消失就归 RESOLVED 是不安全的 → 改为 **ESCALATED**（状态已无法靠自动 Review 可靠维持，需人工）。这比「自动解决」更符合工程事实。

### D15. fingerprint 铁律（升级为 ADR 契约级，**强化 ADR-0025 D6**）

ADR-0025 D6 已实现 `sha256(category-component-root_cause)[:16]`（由 `create_issues.sh` 计算，非 free-form）——物理上已是结构指纹。本扩展将其**升格为不可违反的契约**：

> **`fingerprint` MUST NOT be generated from free-form LLM text.**

生成契约（确定性，与 LLM 措辞无关）：

```
canonical tuple = (category, component, root_cause, symptom?)
      │
      ▼  normalize（lowercase + kebab-case；schema 已强制 component/root_cause ∈ ^[a-z0-9][a-z0-9-]*$）
stable serialization = "category|component|root_cause|symptom"
      │
      ▼  SHA-256 → [:16]
fingerprint
```

- **LLM 措辞变化 ≠ fingerprint 变化**（直接消除我们实测的 MiniMax-M3 不稳定 → fingerprint 漂移 → 重复建 Issue 风险）。
- 新增 `symptom` 进 tuple，提升对 `category+component+root_cause` 相同但语义不同的判别力（补 D6 已知的结构指纹局限）。
- 契约测试：相同归一化 tuple → 相同 fingerprint，与 LLM 输出字符串无关。

### D16. 多 Producer 就绪（扩展性）

Reducer 消费任何带 `producer` 身份的 `review-result.json`。未来 producer 即插即用，**Triage 零重设计**：

```
Claude Review · CI/Test · Security Scan · Dependabot · Coverage Regression ·
E2E Failure · Performance Benchmark · Human Review
        │
        ▼  统一为 Review Result
   Deterministic Reducer → Memory → Triage → Action
```

`producer.name` 进入 Memory 的 `runs/<run_id>.json`，用于溯源与（可选）按 producer 加权。

### D17. 实施分期（扩展，非重写）

- **Phase A**：现有 `claude-review.yml` **新增 emit** —— 除发 Comment 外，把结构化结果写入 `findings.json`（扩展 schema：加 `producer`/`run_id`/`commit_sha`/`status`/`completeness`）；Comment 附 `run_id`+`commit_sha`。**不改文件名**。fingerprint 铁律（D15）即日起生效。
- **Phase B**：从 `create_issues.sh` 抽出 `reduce_review_state.sh`；引入状态机（D14）+ Memory 布局（D13）；把隐性去重提升为**命名 reducer**。
- **Phase C**：Comment **退出 Triage 主链**；Triage 只消费 Memory。`fetch_input.sh` 降级为可选/legacy。
- **Phase D**：接入 CI / Security / 其他 Engineering Signal 作为 producer。

> 已跑通的 `issue-triage.yml` / `findings.schema.json` / `create_issues.sh` / `issue-triage-history` 全部**继续复用**，仅把隐含职责与状态语义显式化——风险最低。

### D18. 治理（沿用 ADR-0025 D8）

本扩展属 Human-Owner 专属文件；AI 仅经独立分支 + PR 提交，**永不经自 merged**。Memory 的运行时写入由 reducer 在受信 `create` job 内执行（系统状态，非 AI 业务改动），其提交/持久化策略由 Human Owner 裁决（见 D13）。

## 被否决方案

| 方案 | 否决理由 |
|---|---|
| Memory 落库进 feature repo（原 D6 Phase C） | 并发 merge 冲突、评审噪音、与「comment 进仓库是噪音」自相矛盾 |
| STALE 自动 RESOLVED | 无证据证明 bug 消失即归 RESOLVED 不安全 → 改 ESCALATED |
| Phase 1 即把 `findings.json` 改名 `review-result.json` |  premature；先复用文件、概念分离，等第二 producer 再拆 |
| Comment 继续作 Triage 输入 | 反模式，已被 Bug 7 / reasoner 0-finding 实证证伪 |
| 单 `state.json` 无 `runs/` 历史 | 无审计性/可追溯性 |
| fingerprint 依赖 LLM 自由文本 | MiniMax-M3 不稳定 → 漂移 → 重复 Issue（实证） |

## 后果与影响（Consequences）

- **正面**：覆盖面从「Claude Review 专用」扩展为「任意 Engineering Signal 统一状态/行动层」；Comment 与状态解耦；具备 stale/escalated 生命周期语义；`run_id` 全链路可追溯；fingerprint 稳定性契约级固化。
- **负面/成本**：新增 reducer 组件；Memory 持久化基础设施；schema 扩展；状态机实现 + 单测。
- **守门**：
  - reducer 必须确定性 + 幂等（fixture 单测覆盖所有转移）。
  - fingerprint 铁律由契约测试强制（相同 tuple → 相同 fp）。
  - Memory 持久化须并发安全（reducer 是 `create` job 内唯一写者）。

---

## 测试要求

- **Reducer 单测**：固定 review-result 驱动状态转移（OPEN→RESOLVED / OPEN→STALE / STALE→ESCALATED / STALE→OPEN 等）。
- **幂等性**：相同输入应用两次 → Memory 字节一致。
- **fingerprint 确定性**：相同归一化 tuple → 相同 fp，与 LLM 措辞无关。
- **schema 契约测试**：review-result 对扩展后的 `findings.schema.json` 校验通过。
- **可追溯性**：Comment 中 `run_id` 能反查 `runs/<run_id>.json` → `memory` 历史。

## 实证基础（Empirical Basis）

- **run `31590878740` 真实创建 Issue #147** → ADR-0025 链路已实证；本扩展是**扩展非重写**。
- **Bug 7**（`Field 'createdBy' doesn't exist on type 'PullRequest'`）+ **reasoner 0-finding / `trust_level=fork`** → 「comment 当数据库」反模式已被亲手证伪，构成本扩展的直接动机。
- **12 个独立缺陷**在 pipeline 各层被修复 → 现有四个「半成品层」确实存在且可工作，本扩展只需把隐含契约显式化。
